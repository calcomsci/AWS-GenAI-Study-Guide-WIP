1. Exam Strategy, Pacing & The "Cut the Crap" (75/25) Method

Topic 01 Exam Strategy & Core Rules

"Cut the Crap" & The 50/50 Tie-Breaker

How the Exam Works: On official AWS AIP-C01 questions, you can usually cut 2 obvious wrong answers right away (50%), leaving a 50/50 choice between the final two believable options. Both finalists usually look like valid AWS setups on paper. Picking the winner comes down to checking the main constraint, the right layer of the stack, and whether every requirement is actually met rather than guessing.

  • Step 1 (Read the Last Sentence First): Start with the final sentence to spot the main goal (least operational overhead, lowest cost, lowest latency, compliance, or finding the root cause).
  • Step 2 (Cut 2 Obvious Wrong Answers): Cross out the 2 clear traps right away—options that fix the wrong part of the system, rely on made-up AWS features, or optimize for the wrong goal.
  • Step 3 (Break the 50/50 Tie): When you're down to the final two (the Winner vs. the Close Runner-Up), use the Three Golden Rules below.
Golden Rule 1: Match the Main Goal in the Final Sentence (Managed Services First) In a 50/50 split, both options usually can work—so stop asking "Is this possible?" and ask "Which option directly answers what the final sentence is asking for?" Unless the question specifically forces custom infrastructure (like custom model weights not supported on Bedrock, payloads/timeouts past serverless limits, or direct GPU control), managed AWS services (Amazon Bedrock features + serverless tools) always beat custom containers, EC2 clusters, or custom-built code on operational overhead and speed.
Golden Rule 2: Fix the Problem in the Layer Where It Happens Every GenAI requirement or bug belongs to a specific part of the stack: Data/Ingestion, Retrieval/Search, Model/Generation, Workflow/State, or Security/Infrastructure. Never pick a tool from one layer to fix a problem in another. Infrastructure and IAM problems show up as clear system or API errors (4xx/5xx, timeouts, access denied), whereas clean logs and metrics with bad answers point to an app or model issue (search quality, prompt wording, model choice, or mismatched embeddings). Likewise, fix search settings when context is missing, and fix prompts, model parameters, or Guardrails when the generated text is the problem.
Golden Rule 3: Meet Every Requirement Without Assuming "Magic" The right answer must cover every mandatory detail in the question (such as real-time vs. background processing, multi-turn chat memory, strict data isolation, or zero-downtime migration) using real, documented AWS features. Cross out the finalist that solves the main problem while ignoring a second requirement, or that assumes an AWS service "automatically" figures out business rules, blocks bad content, or transforms data without the right feature turned on.

Pacing & Stamina Plan (180 Mins / 75 Qs)

  • The 2-Minute Pace: Spend ~1.5 to 2 minutes per question across 75 questions (150 minutes total), saving a clean 30-minute review buffer at the end.
  • The 10-Second Reset: Never close your eyes for 60 seconds on camera (it triggers proctor warnings). Instead: take your hands off the keyboard, look at a neutral spot for 5–10 seconds, take one deep breath, and start the next question.
  • Exam Day Warm-Up: Don't take full practice exams on test day (it drains your focus before the real thing). Review 3 familiar questions 60 minutes before, then stop studying 30 minutes before start time.
  • Break Rules: OnVUE (online) allows a clear glass of water on the desk, and you cannot leave the camera view. Test centers allow unscheduled breaks (the exam clock keeps running), and water stays in your locker.

Core Ground Rules

  • Security First (Unless Told Otherwise): Security is the baseline priority (AWS PrivateLink, IAM least privilege, Guardrails) unless the question asks for a specific single priority. If cost, speed, quick testing, or simplicity is the main goal, pick the option that best meets that goal while keeping sensible security in place.
  • Lambda Is Stateless: AWS Lambda does not keep state between runs. Never store multi-turn chat history or large custom model weights in Lambda memory or /tmp.
  • Diagnose Before Fixing: Finding the root cause (SageMaker Clarify audit, Guardrail Tracing, X-Ray, Logs Insights) must always come before making changes (retraining a model, changing thresholds).
  • Custom Model Rule: Custom fine-tuned model weights require SageMaker Endpoints + ECR or Bedrock Provisioned Throughput (Model Units)—never Bedrock On-Demand.
  • 50/50 Filter: Default to native Bedrock or serverless options when the question asks for least operational overhead or lowest cost. Don't rule out ECS/EKS/GPU clusters when the question specifically asks for strict latency, guaranteed throughput, pre-warmed instances, or custom runtime control.
Topic 02 How to Eliminate Wrong Answers

Good engineering judgment gets you down to two options; knowing how AWS services actually work picks the winner. Common sense is a great filter, but you still need to know real AWS service limits and features. (You won't have internet or AI tools during the exam — rely on how the services actually work.)

Core Principle The exam tests what NOT to do just as much as what to do. Cross out designs that a practical engineer would reject in production: turning off monitoring, removing rollback options during a migration, skipping input checks, or spinning up servers you don't need. Then make sure the remaining option uses a real AWS feature that meets every requirement in the question.

The 4-Step Question Breakdown

Step 1 — Spot the Main Constraint: Read the LAST sentence first. Find what drives the decision: least operational overhead / lowest cost / strict latency / zero downtime.
Step 2 — Check Every Requirement: Note every must-have detail, including words like continuously, in production, without disruption, or across accounts.
Step 3 — Cut the Red Flags: Cross out bad practices, made-up features, unnecessary servers, and options that only solve half the problem. Keep believable options open; don't cross out an answer just because it uses strong wording.
Step 4 — Prove Why It Works: Name the exact AWS feature, setting, trigger, and tradeoff that make the answer work. If you can't explain how it works in one plain sentence, keep checking.

Requirement Scorecard

For each remaining option, mentally check every requirement: ✓ fully met / ~ partly met or needs extra unstated work / ✗ missed, conflicts, or creates a new problem. Pick the option with no ✗ marks and the fewest ~ marks. If two options both have all ✓, break the tie using the main constraint in the final sentence.

Common Wrong-Answer Traps

  • Wrong layer: Trying to fix an infrastructure problem in app code, or a prompt problem with network settings.
  • Half-solution: Solves the main problem but breaks another requirement (for example, cuts cost but breaks compliance).
  • Over-built: Strings together multiple services when a single built-in AWS feature handles it directly.
  • Made-up feature: Names a real AWS service with a realistic-sounding feature that doesn't actually exist.
  • Wrong tradeoff: Optimizes for the wrong goal (for example, fastest speed when the question asked for lowest cost).
Topic 03 Single-Select Strategy (4-Choice Questions)

One option has to solve the whole problem end-to-end. If two answers still look good, compare them against the Requirement Scorecard and check how each service actually works. The winner is the one built for the main goal in the final sentence with the fewest extra moving parts.

Single-Select Tie-Breaker When two remaining options can both work, re-read the last sentence. Does it say least operational overhead? Pick managed Bedrock or serverless. Does it say lowest cost? Compare token pricing and prompt caching. Does it say strict sub-second latency? Look for response caching or provisioned throughput.

The 4 Tiers of Operational Overhead

When the final sentence asks for "LEAST operational overhead" (or "minimal management overhead"), AWS options fall into these 4 tiers from simplest to heaviest. Always pick the highest tier (closest to Tier 1) that meets every requirement in the question:

Tier AWS Category Key Services & Features How to Use on the Exam
Tier 1: Managed GenAI Features Zero Server Management: Built-in AWS AI features with no servers to run. Amazon Bedrock Knowledge Bases, Bedrock Agents, Bedrock Prompt Management, Bedrock Guardrails, Converse API, Bedrock Model Evaluation. ✓ Automatic Winner whenever the built-in feature covers the requirement.
Tier 2: Serverless Glue Zero Cluster Management: Event-driven functions, managed APIs, serverless databases. AWS Lambda, Amazon API Gateway (WebSocket / HTTP), OpenSearch Serverless (AOSS), DynamoDB, S3, Step Functions. ✓ Best Supporting Tools: Pair with Tier 1 for custom routing, streaming, and data prep.
Tier 3: Managed Containers Container Management: Dockerfiles, ECR image scanning, task definitions, cluster scaling. Amazon ECS (Fargate/EC2), Amazon EKS, Application Load Balancers (ALB), custom Docker containers. ✗ Cut whenever Tier 1 or Tier 2 can do the job. Keep only if payloads >6 MB, runtimes >15 min, or custom GPU containers are required.
Tier 4: Self-Hosted / Custom DIY Heavy Server Work: OS patching, scaling, custom code, training pipelines. EC2 GPU instances, self-hosted vector databases (Milvus/Pinecone on EC2), custom Python text chunkers, SageMaker training pipelines for simple ranking. ✗ Cut Immediately: Always wrong when the question asks for "least overhead."

Named-Feature Rule

When a question asks which Bedrock, AgentCore, SageMaker, Guardrails, or CloudWatch feature handles a task, look for the official built-in feature name. Don't pick a custom DIY setup unless the built-in feature can't meet the requirement. Know the difference between similar features: online vs. on-demand evaluation; knowledge-base ingestion logs vs. model invocation logs vs. CloudTrail; Prompt Management vs. prompt caching vs. response caching.

Topic 04 Checking Absolute Words ("Always", "Never", "Automatically")

Words like always, never, immediately, solely, and automatically are signals to double-check how the AWS service actually works — not automatic reasons to cross out an answer.

  • Cross out the option when the claim goes against the question's requirements or how AWS actually works.
  • Keep it when a strict security, compliance, or availability requirement calls for it and AWS supports that behavior.
  • Without configuration is usually a red flag unless the service truly does that by default out of the box.
  • Automatically detects / infers / decides requires a real classifier, evaluator, threshold, rule, or built-in feature.
Bottom line: Common sense cuts bad designs; knowing how AWS works picks the right one. Keep baseline metrics during migrations, monitor old and new setups side by side before cutting over, and check that the service + settings + workload all fit before locking in your answer.

2. How to Pair Answers on Multi-Select Questions (Pick Two / Pick Three)

Topic 05 Pairing Answers on Multi-Select Questions (Pick Two / Pick Three)
Why "Pick Two" Questions Are Harder 5-choice "Select Two" questions have 10 possible pairs (C(5,2) = 10). Guessing blind yields only a 10% chance (vs. 25% on single-select), and AWS awards zero partial credit. AWS intentionally includes options that are individually true statements about AWS, but only solve half the scenario or duplicate the other selected answer. A senior engineer must pair two complementary capabilities that jointly satisfy every scenario constraint without functional overlap.

The Two-Part Question Rule (The Core Pairing Secret)

Over 90% of multi-select questions ask for two separate requirements in the question:

  • Requirement A (How It Runs): Lower latency, better search ranking, caching, streaming, or workflow steps.
  • Requirement B (Safety & Security): Hiding PII, private networking/encryption, blocking prompt attacks, audit logs, or compliance rules.
The Two-Requirement Rule: One right answer solves Requirement A; the second right answer solves Requirement B. If you pick two answers that both solve Requirement A (like two caching tools or two chunking settings), Requirement B is left completely unsolved and your pair is wrong.

How to Find the Right Pair in 5 Steps

Step 1 — Split the Question: Read the final sentence. Spot Requirement 1 (like latency/cost) and Requirement 2 (like security/safety).
Step 2 — Label Each Option's Job: Note which stage of the pipeline each option belongs to (Input / Search / Ranking / Model / Output / Monitoring) and what job it does.
Step 3 — Cut Duplicates Doing the Same Job: If Option B and Option D both handle ranking, they are competing for the same spot. Keep the managed low-overhead option; cut the custom DIY option. Never pick two options doing the exact same job.
Step 4 — Cut Clashing Setups: If Option A uses managed Bedrock Knowledge Bases and Option C requires running your own OpenSearch cluster on EC2, they don't belong together. Drop the setup that breaks the question's main constraint.
Step 5 — Check for Made-Up Features: Check the two remaining options on their own. Do they name real AWS features? Are there fake features (like a "CloudFront throttling policy")? If both are real, don't overlap, and cover both requirements, lock in the pair.

Worked Example: "RAG App Returns 'No Relevant Information Found' After Lambda Update" (Official Skill Builder Question)

Question Setup: A financial company runs a RAG app with Bedrock embeddings + OpenSearch Service vector store + Lambda. After a code update to the Lambda function, the app starts returning generic fallback answers ("no relevant information found") even for questions that used to work. What the logs show: CloudWatch Logs shows zero errors; AWS X-Ray shows the model call succeeded (200 OK); the OpenSearch cluster is healthy; search speed is normal.

OptionWhy It Works or FailsVerdict
A. The Bedrock FM temperature parameter was increased. Temperature only controls randomness in generated text. It is never used by embedding models, and it cannot cause a vector search to return zero matching documents. ✗ Trap (Wrong Layer): Mixes up text generation settings with document search.
B. The updated Lambda function uses a different version of the embedding model. Embedding Drift: New search queries are turned into vectors using a different model version than the documents already stored in OpenSearch. Because the numbers don't line up, similarity scores drop below the cutoff and return 0 matches—while every service still returns 200 OK with zero errors. ✓ Winner: Mismatched embedding versions explain both the missing results and the clean logs.
C. The document embeddings in OpenSearch were deleted during the update. The 50/50 Trap: If documents or indexes were deleted, OpenSearch would log index errors or change query behavior. The question specifically says zero errors, healthy cluster, and normal search latency—meaning the documents are still there, just not matching. Also, updating Lambda code doesn't delete data in OpenSearch. ✗ Cut (Ruled Out by Logs): Clean logs and normal search speed prove the data wasn't deleted.
D. The Lambda IAM role is missing bedrock:InvokeModel permission. A missing IAM permission immediately throws an AccessDeniedException (HTTP 403) in CloudWatch and marks the X-Ray trace as failed. The question states that model calls succeeded and CloudWatch has zero errors. ✗ Trap (Ruled Out by X-Ray): Directly contradicts the 200 OK logs in the question.
The 50/50 Takeaway (B vs C): Both B and C could explain "no results found." To break the tie, look at the logs: Clean CloudWatch + Healthy Cluster + Normal Speed = the database and data are fine (C is wrong). The mismatch is in the embedding versions (B is right).

On AWS Professional exams, a question with 4 requirements needs an answer that covers all 4 requirements. As long as every feature is real, fits the job, and is serverless, it's the right answer. Options B, C, and D aren't wrong because they have fewer buzzwords—they're wrong because they break streaming (REST API), add unnecessary servers (ECS), or use slow background queues for live clicks (SQS).

Topic 07 End-to-End RAG Pipeline
  1. Step 1 • Input: Query Prep: User sends a question through API Gateway. If needed, the app rewrites or breaks down the question for multi-turn chat context.
  2. Step 2 • Vectorize: Query Embedding: The question is sent to the exact same embedding model used when indexing documents (e.g., Titan Text Embeddings V2) to turn it into a vector.
  3. Step 3 • Search: Vector / Hybrid Search: Runs k-NN / HNSW vector similarity search (+ optional BM25 keyword search and recency filters) in OpenSearch Serverless or Aurora pgvector. k-NN Tradeoff: Raising k pulls in more matches (higher recall) but slows down search; lowering k speeds up search but can miss matches.
  4. Step 4 • Filter: Reranking: Top matches pass through a Reranker model (e.g., Cohere Rerank) to score how well each chunk actually answers the question and drop weak matches.
  5. Step 5 • Build Prompt: Prompt Assembly: Bedrock Prompt Management combines the best chunks, system instructions, and the user's question into one structured prompt (separated cleanly with XML tags).
  6. Step 6 • Generate: Model Call & Guardrails: Amazon Bedrock Guardrails checks the input for prompt attacks and jailbreaks, calls the Foundation Model, and checks the output for grounding (no hallucinations) and PII.
  7. Step 7 • Output: Streaming & Citations: Response tokens and source citations stream back live to the user via InvokeModelWithResponseStream + WebSockets / SSE.
Request flowFrom user question to final answer: user prompt enters the app > input check and auth > prompt assembly > search and reranking > model call > guardrails and safety checks > live token streaming or final response > logging and metrics.

Topic 09 How Vector Stores Work & Performance Tuning

Vector databases store numerical embeddings for meaning-based search. Knowing how they index and scale helps you spot why search slows down:

  • HNSW vs. Flat (Brute Force): HNSW (Hierarchical Navigable Small World) builds multi-layer graphs for fast Approximate Nearest Neighbor (ANN) search in O(log N) time. A Flat index checks every single vector one by one in O(N) time. Always use HNSW at scale; Flat gives 100% exact matches on tiny datasets (<10k), but gets painfully slow as data grows.
  • The k-NN Tradeoff (Recall vs. Speed): k sets how many nearest matches to pull back. Raising k pulls back more candidates (helping rerankers), but searches deeper and sorts more items, which slows down search. Raising k never fixes slow search.
  • Segments & Refresh Interval (OpenSearch / Lucene): OpenSearch writes new vectors into separate Lucene segments on every refresh (default: 1 second). Because each segment builds its own HNSW graph, every search has to check all active segments and merge the results. Constant updates with a 1-second refresh create dozens of tiny segments and slow searches down. Fix: Increase index.refresh_interval (e.g., 30s–120s) so vectors batch into fewer, larger segments.
  • OpenSearch Serverless (AOSS) Limits: AOSS automatically scales capacity using OpenSearch Compute Units (OCUs). AWS manages shards and replicas behind the scenes—you cannot manually tune shard counts or replicas on OpenSearch Serverless.
  • Filter Metadata First: Filtering by metadata (like date, department, or category) before running vector math shrinks the search pool early and speeds up queries much more than tweaking k.
OpenSearch slows down as index grows → Increase refresh interval (fewer segments/HNSW graphs); cross out shard/replica tuning on Serverless (AWS manages it via OCUs).
Topic 10 Prompting, RAG & Vector Storage

Hybrid search / duplicate results

🟢 Target: Combine keyword and vector search, remove duplicates by document ID or text, and merge scores before reranking.
🔴 Eliminate: Keeping keyword and vector results as two separate final answers, or turning off keyword search when the question asks for hybrid search.

Relevant results ranked too low / minimal overhead

🟢 Target: Amazon Bedrock reranker models (Amazon Rerank, Cohere Rerank) on Knowledge Bases retrieval, paired with Knowledge Bases hybrid search when exact keywords also matter.
🔴 Eliminate: OpenSearch Learning to Rank, custom pgvector scoring code, or custom-built ranking models—they all need training data or custom code and break "minimal overhead."

Embedding Consistency & Embedding Drift (Official Exam Concept)

🟢 Target (Same Embedding Model): Use the exact same embedding model, version, and vector size for both indexing documents and searching queries.
🔴 Eliminate: Mixing embeddings from different models or versions in the same index, because their numbers don't share the same coordinate space.
What Embedding Drift Is & How to Spot It Embedding Drift happens when your app uses a different model (or version) to embed user search queries than the one used to embed the stored documents (for example, updating a Lambda function from Titan Text Embeddings v1 to v2 without re-indexing OpenSearch).
Symptom: The app starts returning "no relevant information found" even for questions that used to work.
What the Logs Show: Zero CloudWatch errors, X-Ray shows 200 OK model calls, and the vector database is healthy with normal speed.
Fix: Either re-index all documents in the vector store with the new embedding model version, or switch the Lambda query code back to the original embedding model version.

Retrieval Failure vs. Generation Failure (The Temperature Trap)

Retrieval Failure: The pipeline fails to retrieve relevant context from the vector database. Symptoms: "no relevant information found", missing citations, empty retrieved chunks. Root causes: Embedding drift, poor chunking strategy, similarity threshold set too high, missing hybrid search/reranker.
Generation Failure: Context documents were successfully retrieved, but the LLM output is hallucinated, contradictory, overly creative, or fails to follow formatting. Root causes: Temperature too high, Top-P too high, system prompt lacks grounding constraints.
Poison Pill Trap: Never select "increase/decrease temperature" to resolve a retrieval failure ("no information found"). Temperature controls token sampling probabilities during text generation; it has zero impact on vector search or embedding generation.

GraphRAG / Graph relationships + vector similarity

🟢 Target: Amazon Neptune Analytics when the requirement combines related documents or entities, graph structure, and vector similarity search.
🔴 Eliminate: Treating a standalone vector store as the GraphRAG answer when the question specifically requires graph relationships or graph traversal.
S3 prompt-template governanceWhen S3 Versioning is enabled, teams can retain and restore previous versions of stored template objects.
Topic 11 Data Preparation

Quality data improves both retrieval and customization. Remove duplicates, resolve encoding problems, preserve useful structure, and document provenance.

  2. Clean, normalize, deduplicate, and redact.
  3. Split into representative training, validation, and test sets.
  4. Inspect labels and balance important classes.
  5. Track versions, sources, owners, and quality metrics.

4. Foundation Models, Amazon Bedrock & Prompt Engineering

Topic 13 Generative AI Basics

Generative AI creates new content such as text, images, audio, code, and synthetic data from learned patterns. A foundation model is a large, general-purpose model trained on broad data and adapted to many downstream tasks.

RememberModel output is probabilistic. A fluent response is not automatically factual, current, or safe.

Common model tasks

  • Summarization: compress information while preserving key meaning.
  • Classification: assign labels, sentiment, intent, or topic.
  • Extraction: return structured fields from unstructured text.
  • Question answering: generate an answer from learned knowledge or supplied context.
  • Transformation: translate, rewrite, format, or generate code.
Topic 14 Foundation Model Workflow
StagePurpose
Pre-trainingLearn general language or multimodal patterns from large, diverse datasets.
AdaptationSpecialize behavior with prompting, fine-tuning, or preference optimization.
InferenceUse the model to produce a response for a particular request and context.
EvaluationMeasure quality, safety, latency, cost, robustness, and business fit.

Parameters are learned numerical values. More parameters can increase capability, but does not guarantee better results for every task.

Topic 15 Prompt Engineering

A strong prompt gives the model a clear task, relevant context, constraints, and an output format. Put instructions where they are easy to distinguish from untrusted input.

Task + Context + Constraints + Examples + Output format
  • Zero-shot: request a task without examples.
  • Few-shot: show representative input and output examples.
  • Chain-of-thought: for internal reasoning needs, request a concise answer or rationale appropriate to the use case rather than exposing sensitive reasoning.
  • Iterate with evaluation data; change one prompt variable at a time.
Topic 16 Amazon Bedrock

Amazon Bedrock is a fully managed service for building generative AI applications with foundation models from multiple providers through a unified API. It supports model choice, experimentation, customization, agents, guardrails, and knowledge bases.

RAG retrieves relevant chunks, adds them to the prompt, and asks the model to answer from that context. Chunking, metadata filters, embeddings, and reranking affect retrieval quality.

Structured data ruleFor tables, CSVs, JSON, and other structured sources, use format-aware chunking that preserves schema boundaries and row/column relationships. Generic semantic chunking can keep the raw text but still destroy meaning by splitting tables across boundaries.
Preserve existing systemsWhen the requirement says to keep the existing codebase, architecture, or platform unchanged, prefer an adapter, compatibility layer, or minimal integration point over rewriting, replacing, or replatforming the current system. The goal is to add capability without breaking the consuming application.
Reduce vector search scopeWhen a RAG system has a very large document set, narrowing the search space with metadata filters or hierarchical indexes before similarity search often reduces latency much more than simply adjusting the number of retrieved chunks. Search a smaller relevant subset first; only then run vector similarity on that candidate set.

Topic 19 State Management & Integration

Stateless compute / Simple independent lookups

🟢 Target: AWS Lambda, Raw Bedrock InvokeModel API, and Stateless MCP servers.
🔴 Eliminate: Provisioning persistent EC2 instances or attempting to persist session context in Lambda memory.

🟢 Target: Amazon Bedrock Agents, Amazon DynamoDB keyed by sessionId + TTL, and AWS Step Functions Task Tokens.
🔴 Eliminate: Storing state in Lambda /tmp memory, passing entire untrimmed raw chat history from the client, and synchronous sleep loops in Lambda.

Multi-agent orchestration / shared persistent state

🟢 Target: Amazon Bedrock AgentCore Memory for managed shared memory across orchestrator and worker agents in hierarchical task execution.

🟢 Target: Amazon Kinesis Data Streams feeding Lambda or other consumers that invoke Bedrock per batch for near-real-time processing of continuous sensor or event data.
🔴 Eliminate: Scheduled polling, S3 upload triggers, or manual review patterns when the requirement is continuous streaming inference with low latency and event-driven processing.

FM provider outage / Circuit breaker

🟢 Target: AWS Step Functions Circuit Breaker pattern to fail over between foundation models.
🔴 Eliminate: Route 53 Multi-Region failover and Bedrock Cross-Region Inference.

6. Monitoring, Security, Guardrails & Evaluation

Topic 24 Safety, Security & Networking

Cross-Region Inference / compliance boundaries

🟢 Target: Same-region inference for regulated workloads, or use explicit regional controls and networking patterns when data residency is required.
🔴 Eliminate: Treating Cross-Region Inference as compliant by default. Data can cross regions and fall under different legal rules.

Blocking PII on Input & Output

🟢 Target: Amazon Comprehend (DetectPiiEntities) for scrubbing text before ingestion or calling the model; Bedrock Guardrails Sensitive Information Filters to mask PII in model outputs. (Amazon Rekognition for images).
🔴 Eliminate: Relying only on prompt wording ("do not output SSNs") or mixing up Comprehend text detection with KMS disk encryption.

Prompt Attack Detection & Jailbreak Defense

🟢 Target: Bedrock Guardrails content and prompt-attack filters to block prompt injection, jailbreaks, and role-play bypasses. Turn on "trace": "enabled" and check GuardrailPolicyType to find the root cause.
🔴 Eliminate: Using AWS WAF to block conversational jailbreaks (WAF handles HTTP/DDoS/rate limits, not prompt meaning), or writing custom regex in Lambda.

S3 Cross-Region Replication (CRR) / Data Residency

🟢 Target: Keep encryption and access policies intact during replication, and check data residency rules before copying GenAI training data to another region.
🔴 Eliminate: Assuming S3 CRR automatically removes PII in transit or strips encryption.
Topic 25 Testing, Evaluation & Monitoring

Full-stack monitoring setup

🟢 Target: Combine CloudWatch metrics, AWS X-Ray tracing, Bedrock Model Invocation Logging, and Amazon Managed Grafana.
🔴 Eliminate: Using CloudWatch metrics by themselves or only checking logs once a week in batches.

Multi-agent systems / tracking across agents

🟢 Target: Track each agent's latency, token usage, tool calls, retries, and handoffs, and connect traces end-to-end to spot slowdowns or failures.
🔴 Eliminate: Watching only one summary dashboard or only the busiest agent when trying to debug multi-agent handoff issues.

Alerting / set a baseline first

🟢 Target: Measure normal GenAI behavior first before setting alert thresholds, then alert when latency, token usage, error rate, or quality shifts significantly.
🔴 Eliminate: Alerting on every tiny bump, turning off monitoring during a rollout, or picking random thresholds without a baseline.

Bedrock RAG Evaluation: Citation Metrics

🟢 Target: Citation Coverage to measure how much of the answer is backed by sources, and Citation Precision to check whether the cited sources actually support the claim.
🔴 Eliminate: Claims that coverage only applies to text while precision applies to images, or that citation metrics measure speed.

Topic 28 Security, PII, Guardrails & RAG Evaluation
  • Blocking PII on Input & Output: Use Amazon Comprehend (DetectPiiEntities) to scrub text before indexing or calling a model; use Bedrock Guardrails Sensitive Information Filters to mask PII in model outputs. (Use Amazon Rekognition for images).
  • Prompt Attack Detection: Bedrock Guardrails filters detect and block jailbreaks, prompt injections, and role-play tricks.
  • Debugging Blocked Guardrail Requests: Turn on "trace": "enabled" and check GuardrailPolicyType (Content, Topic, SensitiveInformation, ContextualGrounding).
  • Secrets & Networking: Store API keys in AWS Secrets Manager with automatic rotation and KMS encryption. Keep network traffic private with AWS PrivateLink (Interface VPC Endpoints).
  • S3 Cross-Region Replication (CRR): Keeps encryption and permissions intact, but copying GenAI training data across regions can break data residency & compliance rules (and CRR never removes PII automatically).
  • RAG Evaluation Metrics:
    • Faithfulness / Contextual Grounding: Checks if the answer is actually backed by the retrieved text (catches hallucinations; much better than BLEU/ROUGE word-overlap scores).
    • Citation Coverage (Recall): How much of the answer is backed by source citations.
    • Citation Precision (Accuracy): Whether the cited sources actually back up the claim they're attached to.

7. Cost Optimization, Caching & Performance Signals

Topic 32 Cost Optimization

Predictable queries / Reduce time to first token

🟢 Target: Pre-compute responses for common, predictable queries and serve them from an application-level response cache before invoking the Bedrock foundation model. A cache hit avoids model inference, reducing time to first token, latency, and token charges.
🔴 Eliminate: Increasing temperature, adding more few-shot examples, or assuming the InvokeModel API is inherently faster than the Converse API.
Response caching stores completed answers. Prompt Caching stores reusable prompt prefixes and still invokes the model.

Repeated system prompt + similar FAQ queries / Two-layer caching

🟢 Target: Combine Bedrock Prompt Caching for repeated system-prompt prefixes with semantic caching for similar FAQ queries. Prompt caching reduces repeated input-token charges; semantic-cache hits return stored responses without invoking the model.
🔴 Eliminate: Treating prompt caching and semantic caching as interchangeable: one reuses prompt context, while the other reuses completed answers for semantically similar requests.

Most cost-effective / Reduce token billing spend

🟢 Target: Prompt Caching for static prompt prefixes > 1,024 tokens, Batch Inference for offline processing, Model Right-Sizing, and S3 Vectors.
🔴 Eliminate: Idle dedicated instances like SageMaker multi-GPU endpoints, Flagship over-provisioning, and full raw document injection.

Using overall call-count alarms alone to explain why one request failed; treating a simple source tag as a full trace. Offline Model Evaluation compares model quality before launch; it doesn't replace live production logs.
Private networking / data isolation Use AWS PrivateLink interface VPC endpoints for private service access, paired with endpoint policies, security groups, and IAM permissions. Using public internet endpoints when private networking is required; relying on an S3 bucket policy alone to keep network traffic off the public internet; confusing multi-Region setup with private networking.
Bounded agent loops / stopping conditions For custom loops, set max step limits and timeouts and check for a clear completion state in your code; use built-in Bedrock Agent limits as documented. Assuming an agent will magically spot a runaway loop or stop at a business goal without a step limit or completion check.
Document preparation / LLM ingestion Configure Knowledge Bases parsing/chunking, or build data prep steps with Glue/Lambda. Use Bedrock Data Automation to extract structured data from documents and media. Assuming S3 automatically cleans, chunks, or reformats files to fit a model's context window on its own.
Troubleshoot KB ingestion / failed documents Send Knowledge Base logs to Amazon CloudWatch Logs; search with CloudWatch Logs Insights for per-document error codes (RESOURCE_IGNORED, EMBEDDING_FAILED, INDEXING_FAILED). Using CloudTrail (only logs API calls like StartIngestionJob, not which individual files failed); using Model Invocation Logging (logs live model prompts, not document ingestion jobs); using Application Signals.
Analyze photos/video / summarize trends Pick a Bedrock model that supports the media type you need. The model reads the images/video; Step Functions can coordinate multi-step calls and retries; save structured results in S3 and chart them in QuickSight. Assuming every multimodal model accepts video; treating Step Functions or QuickSight as the AI model that reads the image; using an image-generator model to analyze photos.
Large payload (> 6 MB, e.g. 50 MB) / long processing (> 60s, e.g. 15 min) / on-demand GPU Deploy a SageMaker Asynchronous Inference endpoint on GPU instances; handles large payloads up to 1 GB via S3, runtimes up to 1 hour, on-demand calls (InvokeEndpointAsync), and scales down to 0 instances when idle. Real-Time Inference (6 MB payload limit, 60s timeout limit); Serverless Inference (4 MB payload limit, 60s timeout, CPU only / no GPUs); Batch Transform (offline batch job that spins up and tears down clusters, not an on-demand endpoint).
Migrating On-Demand Bedrock → Provisioned Throughput / keeping monitoring intact Run side-by-side monitoring for both modes during the switch. Track metrics for both on-demand model IDs and provisioned model ARNs to compare p95/p99 latency (TTFT), token throughput, and InvocationUtilization; shift traffic gradually with weighted routing. Turn off old alarms only after the new setup is stable. Turning off on-demand metrics right away when provisioning (loses your baseline comparison); dropping speed dashboards to only watch cost; watching account quota pages instead of actual CloudWatch call metrics; assuming provisioned throughput means you never need ThrottlingException (429) alarms.
Rule of thumb: check that the AWS feature exists, is configured properly, and fits the workload. Treat words like "automatically," "natively," and "for every model" as claims to double-check, not automatic wrong answers.
