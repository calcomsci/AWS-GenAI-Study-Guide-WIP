1. Exam Strategy, Pacing & The "Cut the Crap" Answer Elimination Method

Exam Strategy & Core Rules

"Cut the Crap" Answer Elimination Method

What "Cut the Crap" Means: Every AWS AIP-C01 question surrounds the right answer(s) with 3 wrong answers (distractors) designed to mislead candidates—whether it is a standard 4-choice question (1 right answer, 3 distractors) or a 5-choice "Select TWO" question (2 right answers, 3 distractors). "Cut the Crap" means eliminating all 3 distractors so candidates can decisively select the right answer(s) without second-guessing—by verifying constraint fit, architectural boundaries, and requirement completeness.

  • Step 1 (Reverse-Read): Read the final sentence first to lock onto the exact binding constraint (least operational overhead, cost optimization, latency, governance/compliance, or root-cause diagnosis) and note whether the question requires 1 or 2 answers.
  • Step 2 (Cut the Obvious Distractors): Eliminate the obvious distractors immediately—options operating at the wrong architectural layer, relying on fabricated service capabilities, or optimizing for the opposite tradeoff.
  • Step 3 (Cut the Final Distractor Decisively): Apply the Three Golden Rules below to expose the subtle flaw in the remaining near-miss distractor, eliminating all 3 wrong answers and locking onto the winner with certainty.
Golden Rule 1: Optimize for the Binding Constraint (Managed-First by Default) When two options look like they can work on paper, stop asking "Is this possible?" and ask "Which option directly satisfies the final sentence's primary constraint?" Unless the stem explicitly forces custom infrastructure (e.g., custom model weights not supported on Bedrock, payloads/timeouts exceeding serverless limits, or specialized GPU runtime control), native managed capabilities (Amazon Bedrock features + serverless glue) always beat custom containers, EC2 clusters, or custom code on operational overhead and agility.
Golden Rule 2: Match the Architectural Layer & Failure Domain Every GenAI requirement or failure lives in a specific layer: Data/Ingestion, Retrieval/Indexing, Model/Generation, Orchestration/State, or Security/Infrastructure. Never select a solution from one layer to fix a problem in another. Infrastructure and IAM failures surface as explicit API/system errors (4xx/5xx, timeouts, access denied), whereas healthy telemetry with poor outputs points to the semantic/application layer (retrieval quality, prompt design, model selection, or data drift). Similarly, tune retrieval mechanisms to fix missing context, and tune prompts, inference parameters, or Guardrails to control generation behavior.
Golden Rule 3: 100% Requirement Coverage with Zero Unstated Magic The winning answer must satisfy every mandatory qualifier in the scenario (e.g., real-time vs. asynchronous, multi-turn state, regulatory isolation, zero-downtime migration) using documented AWS behavior. Eliminate any option that solves the headline problem while violating a secondary constraint, or that assumes a service "automatically" infers business logic, enforces safety, or transforms data without the required native feature and configuration.

* Author's Footnote (Why the "50/50 Elimination Method" is Deprecated): While the 50/50 elimination method was an earlier crutch used by the author and works reasonably well at first glance, the author has deprecated this method and discourages candidates from relying on it. A "50/50" approach implies removing only 2 of the wrong answers in a 4-choice question, leaving the test-taker hesitating between two plausible-looking answers when only 1 is actually correct. Rather than stopping at a 50/50 split, candidates should apply the "Cut the Crap" Answer Elimination Method to eliminate all 3 distractors and select the single right answer decisively.

  • The 10-Second Micro-Reset: Never close your eyes for 60 seconds on camera (triggers proctor alerts). Instead: drop hands from keyboard, look at a neutral spot for 5–10 seconds, take one deep breath, and attack the next stem.

Core Rules

  • The Well-Architected Baseline: Security is the default foundational priority (AWS PrivateLink, IAM least privilege, Guardrails) unless overridden by a specific single constraint. If cost, speed, experimentation, or simplicity is the actual constraint, choose the option that best satisfies it while still applying reasonable security controls.
  • The Ephemeral Compute Law: AWS Lambda is strictly stateless. Never store multi-turn chat history or large custom model weights in Lambda memory or /tmp.
  • Diagnostics-First Law: Root-cause inspection (SageMaker Clarify audit, Guardrail Tracing, X-Ray, Logs Insights) must always precede remediation (retraining, threshold changes).
  • Custom Model Rule: Custom fine-tuned model weights require SageMaker Endpoints + ECR or Bedrock Provisioned Throughput (Model Units)—never Bedrock On-Demand.
  • Managed-First Filter: Default to native Bedrock or serverless options when the requirement is least operational overhead or lowest cost. Do not eliminate ECS/EKS/GPU cluster patterns outright when the requirement explicitly calls for strict latency, guaranteed throughput, pre-warmed inference, or specialized runtime control.
The Intuitive Elimination Guide

Engineering judgment cuts the obvious distractors; AWS feature knowledge eliminates the final near-miss distractor so candidates can decisively select the winner. Common sense is a powerful filter, not a substitute for knowing documented service capabilities, limits, and configuration boundaries. (No internet or AI tools are available during the exam — candidates must rely on their own mental model.)

Core Principle The exam tests what NOT to do as much as what to do. Eliminate designs that a senior engineer would reject in production: dropping observability, removing rollback paths during a migration, skipping validation, or adding unjustified infrastructure. Then prove that the surviving option is a real AWS capability that satisfies every stated requirement.

The 4-Step Decision Check

Pass 1 — Constraint Anchor: Read the LAST sentence first. Identify the binding driver: least operational overhead / lowest cost / strict latency / zero downtime.
Pass 2 — Requirement Coverage: Mark every non-negotiable, including qualifiers such as continuously, in production, without disruption, or across accounts.
Pass 3 — Red-Flag Purge: Reject anti-patterns, unsupported magic, unjustified infrastructure, and options that solve only part of the scenario. Keep plausible options provisional; do not lock out a candidate merely because wording is strong.
Pass 4 — Proof of Fit: Name the exact AWS feature, configuration, input/event source, and tradeoff that make the answer work. If you cannot explain the mechanism in one sentence, it is not proven.

Requirement Checklist

For each surviving option, silently score every mandatory requirement: ✓ directly met / ~ partly met or needs unstated work / ✗ conflicted, unaddressed, or introduces new risk. Pick the option with no ✗ marks and the fewest ~ marks. If two options both have all ✓, the tie-breaker is always the binding constraint.

Distractor Signatures

  • Self-incriminating payoff clause ("...to identify X"): Read the final clause of each option. Distractors often confess their own limitation at the end of the sentence (e.g., concluding "...to identify which content source triggered interventions" when the stem asked which specific policy rule was invoked and why).
  • Wrong lifecycle phase (Offline vs. Live Runtime): Proposing pre-deployment/offline tools (Bedrock Model Evaluation jobs, synthetic test cases, benchmark dashboards) to diagnose why a live production customer query was just blocked or failed.
  • Telemetry depth mismatch (Count vs. Payload vs. Decision Trace): Using threshold Alarms/Metrics (counts how many) or Invocation Logs (captures raw input/output text) when the question asks for internal decision-making analysis (requires Tracing: "trace": "enabled" or enableTrace: true).
  • Wrong layer: Solving an infrastructure problem in application code, or a retrieval problem with generation parameters (temperature).
  • Partial solution: Solves the main problem but ignores a stated constraint (e.g., reduces cost but breaks compliance or streaming).
  • Over-engineered: Introduces multi-service orchestration or containers when a native managed feature handles it directly.
  • Fabricated capability: Names a real service with a plausible-sounding feature that does not exist in AWS.
  • Opposite tradeoff: Optimizes for the wrong metric (e.g., lowest latency when the question asked for lowest cost).
Single-Select Strategy (4-Choice Questions)

One option must satisfy the full requirement end-to-end. If two answers remain plausible, compare them against the Requirement Checklist and perform the Proof-of-Fit check. The winner is the one whose documented primary purpose matches the binding constraint with the fewest unstated dependencies.

Single-Select Tie-Breaker When two surviving options are technically valid, re-read the last sentence. Does it say least operational overhead? Default to Bedrock serverless. Does it say lowest cost? Compare token charges and prompt caching. Does it say strict sub-second latency? Look for response caching or provisioned throughput.

Named-Feature Rule & Tier 1 Managed-Service Override

When a question asks which Bedrock, AgentCore, SageMaker, Guardrails, or CloudWatch feature provides a behavior, expect a named managed capability. Do not substitute a reasonable DIY architecture unless the managed feature cannot meet the requirement. Learn lifecycle distinctions: online vs. on-demand evaluation; knowledge-base ingestion logs vs. model invocation logs vs. CloudTrail; Prompt Management vs. prompt caching vs. response caching.

The Tier 1 Managed-Service Override Rule (Never Pick Custom DynamoDB Over Native Bedrock Features) On any question whose binding constraint is "MINIMAL / LEAST operational overhead", AWS exam writers treat building custom tables or workflows in Amazon DynamoDB / EventBridge / Lambda as high-overhead custom development whenever a native Tier 1 Bedrock feature exists for that domain. Specifically, for prompt template storage, versioning, parameterization, and multi-stage approval governance across business units, always choose Amazon Bedrock Prompt Management (with IAM authorization policies) over storing prompt templates in a custom DynamoDB table—even when the option attributes generous approval/collaboration capabilities to Bedrock Prompt Management.
Absolute-Language Verification

Words such as always, never, immediately, solely, and automatically are prompts to verify a service boundary — not instant disqualifiers.

  • Eliminate the option when the claim conflicts with the requirements or documented behavior.
  • Keep it when a stated security, compliance, reliability, or availability requirement justifies the strong language and AWS supports the capability.
  • Without configuration is suspect unless the service explicitly performs that behavior by default.
  • Automatically detects / infers / decides requires a documented classifier, evaluator, threshold, rule, or managed feature.
Final rule: Common sense eliminates bad architecture; AWS service knowledge chooses the supported one. Preserve baselines during migrations, use canary or parallel telemetry when appropriate, and verify capability + configuration + workload fit before committing.

2. The 4 Universal Distractor Confession Patterns ("Cutting the Crap" Without Documentation)

When you encounter unfamiliar API parameters or metrics on the exam, you don't need AWS documentation to spot the distractors—wrong answers betray themselves through 4 structural flaws:

Pattern 1 • Read the Last 8 Words
The Self-Incriminating Payoff Clause: Read the final "...to identify X" or "...to ensure Y" clause of each option. Distractors regularly confess they solve the wrong problem at the very end of the option (e.g., ending with "...to identify which content source triggered interventions" when the stem asked which specific rule was invoked and why).
Pattern 2 • Check the Clock
The Lifecycle Phase Mismatch: Never use an offline/pre-deployment benchmarking tool (Bedrock Model Evaluation jobs, synthetic company test cases, batch jobs) to diagnose why a live production customer query was just blocked or failed—or vice versa.
Pattern 3 • Check What You Already Know
Redundant Discovery of a Stated Fact: If the stem already tells you "When a customer query is blocked...", any option that builds a pipeline to figure out whether the block happened on the input vs. the output (GuardrailContentSource) is wasting effort discovering a fact the question already gave you.
Pattern 4 • Match the Telemetry Depth
Alarms vs. Logs vs. Trace: Alarms/Metrics only tell you that a count crossed a threshold. Invocation Logs only show raw request/response text. Whenever the stem asks for internal decision-making, which specific rule fired, why content was flagged, or step-by-step agent reasoning, the answer is always Tracing ("trace": "enabled" or enableTrace: true).

Diagnosing RAG Retrieval Failure After a Code Update (Embedding Drift vs. Generation & Infrastructure)
Official AWS Skill Builder Question:

A financial services company operates RAG for an application that answers user questions by using internal market analysis reports. The application uses Amazon Bedrock for the embedding model. The application uses an Amazon OpenSearch Service cluster as the vector store. An AWS Lambda function performs the embedding and search logic. After a recent code update to the Lambda function, the application starts returning generic responses. For example, the application returns "no relevant information found" even for questions that previously returned accurate answers. Amazon CloudWatch Logs shows no errors. AWS X-Ray confirms successful FM invocation. The OpenSearch Service cluster is healthy. Query latency remains normal. What is the cause of this issue?

Official Verified Answer: Option B
Step-by-Step Systematic Option Dissection & Elimination:
  • ❌ Option A (ELIMINATE): The Amazon Bedrock FM temperature parameter was increased. Temperature controls token generation randomness during output creation. The failure occurred during retrieval (returning 'no relevant information found') before generative completion.
  • ✅ Option B (CORRECT): The updated Lambda function uses a different version of the embedding model. When embedding model versions change, vector space geometry shifts (Embedding Drift). Query vectors no longer match pre-indexed document vectors, yielding zero cosine similarity matches while all infrastructure remains 100% healthy.
  • ❌ Option C (ELIMINATE): The document embeddings in OpenSearch Service were deleted during the application update and have not been re-indexed. Contradicted by stated telemetry—the OpenSearch Service cluster is explicitly reported as healthy with normal latency.
  • ❌ Option D (ELIMINATE): The Lambda function's IAM role is missing the permission for bedrock:InvokeModel. Contradicted by stated telemetry—AWS X-Ray explicitly confirms successful FM invocation, and CloudWatch Logs show zero errors.
How the Guide Proves This: By applying Golden Rule 2 (Match the Architectural Layer & Failure Domain), Section 3 (Embedding Drift & The Temperature Trap), and Section 6 (Domain 5 Troubleshooting).

2. Pairing Techniques & Multi-Select Mastery (Pick Two / Pick Three)

Multi-Select Mastery & Advanced Pairing Techniques (Pick Two / Pick Three)
The Mathematical Reality & Double-Trap 5-choice "Select Two" questions have 10 possible pairs (C(5,2) = 10). Guessing blind yields only a 10% chance (vs. 25% on single-select), and AWS awards zero partial credit. AWS intentionally includes options that are individually true statements about AWS, but only solve half the scenario or duplicate the other selected answer. A senior engineer must pair two complementary capabilities that jointly satisfy every scenario constraint without functional overlap.

The Split-Constraint Principle (The Core Pairing Secret)

Over 90% of multi-select questions contain two distinct architectural requirements in the stem:

  • Requirement A (Functional / Operational): Latency reduction, relevance ranking, caching, streaming, or workflow orchestration.
  • Requirement B (Governance / Non-Functional): PII redaction, cryptographic isolation, prompt attack defense, audit logging, or compliance boundaries.
The Two-Requirement Rule: One correct answer solves Requirement A; the second correct answer solves Requirement B. If you pick two answers that both address Requirement A (e.g., two caching layers or two chunking settings), you have left Requirement B completely unresolved. Your pair fails.

The 5-Step Pairing Method

Step 1 — Split the Stem: Read the final sentence. Underline Requirement 1 (e.g. latency/cost) and Requirement 2 (e.g. security/safety).
Step 2 — Functional Tagging: Tag all 5 options with their pipeline stage (Ingress / Retrieval / Rank / Inference / Output / Ops) and functional job.
Step 3 — Purge Redundant Duplicates (Overlap Test): If Option B and Option D both do ranking, they are competing duplicates. Keep the managed low-overhead option; eliminate the custom/DIY option. Never select two options doing the same job at the same stage.
Step 4 — Purge Architectural Clashes: If Option A uses managed Bedrock Knowledge Bases and Option C requires self-hosting an OpenSearch cluster on EC2, they are mutually exclusive architectural tracks. Drop the non-qualifying architecture.
Step 5 — Independent Truth & Distractor Check: Inspect both survivors alone. Do they name real AWS features? Are there fabricated options (like "CloudFront throttling policy")? If both are genuine, non-overlapping, and cover both requirements, lock in the pair.
Multi-Select Trap Signatures: (1) The "Same-Service" False Pair: assuming two options belong together simply because both name "Bedrock Knowledge Bases". (2) The "Mirror Distractor" Mirage: agonizing between two identical-sounding API methods when neither (or only one) is in the true pair. (3) Over-indexing on one layer: picking two retrieval options when the stem asked for retrieval + output PII safety.

Vector Store Mechanics & Performance Tuning

Vector databases store dense embeddings for semantic search. Understanding how they index and scale is critical for troubleshooting retrieval latency:

  • HNSW vs. Flat (Brute Force): HNSW (Hierarchical Navigable Small World) builds multi-layer graphs for Approximate Nearest Neighbor (ANN) search with logarithmic time complexity: O(log N). Flat index performs exhaustive distance comparison across every vector in O(N) time. Always use HNSW at scale; Flat guarantees 100% recall for tiny datasets (<10k), but search latency explodes linearly as the index grows.
  • The k-NN Tradeoff (Recall vs. Latency): k specifies the number of nearest neighbors retrieved. Increasing k retrieves more candidate vectors (improving recall for downstream rerankers), but requires deeper graph traversal and larger candidate sorting, which increases query latency and degrades search performance. It never resolves slow search.
  • Segment Architecture & Refresh Interval (OpenSearch / Lucene): OpenSearch flushes vectors into immutable Lucene segments on every index refresh (default: 1s). Crucially, an HNSW graph is built per segment, and k-NN queries must search every active segment's graph before merging results. Continuous ingestion with frequent refreshes creates dozens of tiny segments, severely degrading search latency as the index grows. Fix: Raise index.refresh_interval (e.g., 30s–120s) so vectors accumulate into fewer, larger segments with unified HNSW graphs.
  • OpenSearch Serverless (AOSS) Boundaries: AOSS automatically provisions and scales OpenSearch Compute Units (OCUs) for ingestion and search. Shards and replicas are completely managed and abstracted by AWS; developers cannot configure shard counts or search replicas for Serverless collections.
  • Metadata Pre-filtering: Applying metadata filters before vector distance calculation prunes the candidate search space early, reducing search latency significantly more than adjusting k.
OpenSearch degraded search as index grows → Raise refresh interval (fewer segments/HNSW graphs); eliminate shard/replica tuning on Serverless (managed by OCUs).
RAG Troubleshooting: Embedding Drift & Failure Boundaries

Embedding Consistency & Embedding Drift

Embedding Consistency Rule & Drift Symptoms Rule: Maintain a single embedding model, model version, and vector dimension per index. Never mix embeddings from different models or versions inside the same index, because each encoder maps text into an incompatible coordinate space.
Embedding Drift: Occurs when the model or version generating runtime query embeddings differs from the model that indexed the stored document embeddings (e.g., updating a Lambda function from Titan Text Embeddings v1 to v2 without re-indexing OpenSearch).
Symptom: The RAG pipeline suddenly returns generic fallbacks ("no relevant information found") even for queries that previously succeeded.
Telemetry Footprint: Zero CloudWatch errors, X-Ray confirms 200 OK FM invocation, and the vector store cluster is healthy with normal query latency.
Resolution: Re-index all document embeddings using the new embedding model version, or revert the query embedding code to match the existing index model.

Retrieval Failure vs. Generation Failure (The Temperature Trap)

Retrieval Failure: The pipeline fails to fetch relevant context from the vector database. Symptoms: "no relevant information found", missing citations, or empty retrieved chunks. Root causes: Embedding drift, poor chunking strategy, similarity threshold set too high, or missing hybrid search/reranker.
Generation Failure: Relevant context documents were successfully retrieved, but the LLM output is hallucinated, contradictory, overly creative, or ignores formatting rules. Root causes: Temperature/Top-P set too high, or system prompt lacks explicit grounding constraints.
Boundary Rule: Temperature and Top-P control token sampling probabilities during text generation only — they have zero effect on deterministic embedding generation or vector similarity search.

  2. 2. Create a Test Dataset (The Controlled Inputs): Curate diverse scenarios and edge cases aligned to the approved metrics from Step 1.
  3. 3. Conduct Side-by-Side A/B Testing on the Test Dataset (The Execution): Run both the candidate model and existing production model on the Step 2 dataset and score outputs against Step 1's metrics. (Requires validated metrics + dataset before running; produces raw comparison scores.)
  4. 4. Implement Automated Quality Gates with AWS Step Functions (The Threshold Verification): Enforce automated checkpoints that verify Step 3's test results against predefined approval thresholds before proceeding.
  5. 5. Analyze Results & Generate a Comprehensive Evaluation Report (The Final Decision): Synthesize the threshold-validated findings into a final report to approve replacing the production model.

Offline back-office workloads, nightly summarization, or catalog tagging with no real-time user waiting. Yes (at standard on-demand pay-per-token rates with no extra routing fee). Yes (invokes the smaller/cheaper model for simple prompts and the larger model for complex prompts). Multi-GPU LLM Serving & Container Optimization (SageMaker AI / DJL Serving / vLLM)

When hosting fine-tuned or open-weight LLMs on multi-GPU instances (e.g., Amazon SageMaker AI endpoints with Deep Java Library [DJL] Serving, vLLM, or TGI), throughput, concurrency, and GPU memory utilization are governed by four core serving parameters:

Serving Parameter / Technique How It Works in GPU Memory & Compute Primary Optimization Goal Common Misconception / Distractor Trap
Max Sequence Length & Rolling (Continuous) Batching Serving engines pre-allocate GPU KV-cache memory per slot based on configured max_sequence_length. Lowering max_sequence_length to match real I/O lengths frees VRAM for a larger rolling batch size. Higher Concurrency & Throughput per GPU when actual prompts/completions are much shorter than the default model context limit. Leaving max_sequence_length 10× larger than real traffic wastes KV-cache VRAM and starves rolling batch concurrency.
Tensor Parallelism Degree vs. Model Replicas tensor_parallel_degree splits one model copy across N GPUs. If an instance has 8 GPUs and the model fits in 4 GPUs, setting degree = 4 deploys 2 independent model replicas (8 ÷ 4 = 2) on the same instance. Maximizing Multi-GPU Instance Utilization & Concurrency by running multiple model copies per instance when weights fit on a subset of GPUs. Setting tensor parallelism across all 8 GPUs when the model fits in 4 GPUs restricts the instance to 1 replica and leaves half the GPU capacity underutilized.
Speculative Decoding Uses a small, fast draft model to predict multiple candidate tokens ahead and verifies them in a single forward pass of the target LLM. Reducing Single-Request Output Latency (faster tokens-per-second for an individual user stream). Selecting speculative decoding to fix low GPU memory utilization or increase instance concurrency (the draft model actually consumes extra VRAM).
Model Quantization (FP8 / INT8 / AWQ / GPTQ) Reduces numerical precision of model weights/activations (e.g., FP16 → INT8/FP8/INT4) to shrink the memory footprint per model copy. Fitting Larger Models into Fewer GPUs (reducing required tensor parallelism degree or instance size). Assuming quantization never affects output precision on sensitive mathematical/reasoning tasks without evaluation.

"Multi-GPU LLM serving utilization / low concurrency (DJL Serving on SageMaker)" 1. Reduce maximum sequence length (frees KV-cache memory to support a larger rolling batch size per GPU).
2. Right-size tensor parallelism degree to match the GPUs needed per copy (e.g., degree 4 on an 8-GPU instance to run 2 model replicas per instance).		 Spreading 1 replica across all 8 GPUs (tensor_parallel_degree = 8) when weights fit in 4 GPUs; enabling speculative decoding (improves single-request latency, not resource/memory utilization); adding more underutilized instances.
"Custom agent hosting & shared state (Amazon Bedrock AgentCore)" AgentCore Runtime: Use AgentCore SDK (@app.entrypoint) for automatic HTTP server/endpoint setup + AgentCore starter toolkit for automated container packaging and deployment.
AgentCore Memory: Managed persistent and shared memory across supervisor/worker sub-agents.		 Hand-coding custom FastAPI/Flask web servers (/invocations, /ping), manually managing Dockerfiles/ECS Fargate tasks or SageMaker inference containers when AgentCore is specified, or treating raw S3/ElastiCache as managed multi-agent coordination state.
"Continuous streaming inference / IoT & event streams" Amazon Kinesis Data Streams feeding AWS Lambda consumers that invoke Bedrock per micro-batch in near real time. Scheduled cron polling, periodic S3 upload triggers, or manual batch review patterns.
"Cross-Region Inference (CRIS) — Peak-period throttling vs. data residency" For peak-period throttling ("Too many requests") at lowest cost: Use Cross-Region Inference (CRIS) to automatically distribute burst traffic across Regions in a geographic area using the same FM at on-demand pricing.
For strict single-Region data residency: Keep same-Region inference with PrivateLink.		 Building custom Lambda multi-Region fallback code (unnecessary overhead); using Intelligent Prompt Routing when the same FM is required (Prompt Routing requires 2+ different models); buying Provisioned Throughput for peak-only bursts; using CRIS when strict single-Region residency is mandated.
"Bidirectional PII defense & S3 text redaction for enterprise search" Amazon Comprehend (DetectPiiEntities / PII redaction) to detect and redact PII from S3 text before indexing into Amazon Kendra (managed enterprise search) or invoking an FM; Bedrock Guardrails Sensitive Information Filters to mask output PII (Rekognition for images). Relying on system prompts to remove PII at query time (unreliable and vulnerable to jailbreaks); using Amazon Macie to redact PII (Macie only discovers/scans S3 buckets, does not redact inline text); using Amazon Textract on plain email text; using DocumentDB in place of Amazon Kendra for NLP enterprise search.
"Prompt attack / jailbreak defense & guardrail rule diagnosis" Bedrock Guardrails semantic filters; configure {"trace": "enabled"} in guardrailConfig and filter InvocationsIntervened by GuardrailPolicyType to see which rule fired and why. AWS WAF or Lambda regex for semantic jailbreaks; filtering by GuardrailContentSource (only shows INPUT vs. OUTPUT, not which rule fired); offline Model Evaluation jobs for live blocks.
"S3 Cross-Region Replication (CRR) for GenAI corpora" Preserves encryption and access policies byte-for-byte for disaster recovery, but requires verifying sovereign data-residency boundaries before replicating across regions. Assuming S3 CRR automatically anonymizes/redacts PII in transit or strips encryption.
"Enterprise 4-pillar observability & baseline alerting" CloudWatch metrics + AWS X-Ray traces + Bedrock Model Invocation Logging + Amazon Managed Grafana; establish a normal baseline first, then alert on statistically significant deviations. Isolated CloudWatch metrics alone; weekly batch log polling; alerting on every minor fluctuation without a baseline; disabling monitoring during rollout.
"Multi-agent cross-agent observability" Monitor every agent's latency, token usage, tool calls, retries, and handoffs, and correlate end-to-end traces across the workflow. Monitoring only the single busiest agent or relying on one aggregate dashboard to diagnose inter-agent handoff failures.
"RAG evaluation: Citation Coverage vs. Citation Precision" Citation Coverage (Recall): % of generated claims backed by source citations. Citation Precision (Accuracy): whether cited passages actually substantiate the linked claim. Claiming Coverage applies to text while Precision applies to images, or claiming citation metrics measure pipeline execution speed.
