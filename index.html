01 Top-Down Exam Strategy & Logic Gates

  • Order of Operations: Read the final sentence first to identify the core constraint, such as least operational overhead, most cost-effective, or minimize latency.
  • The Well-Architected Baseline: Security is often the default priority in enterprise design, but the exam should always follow the stated requirement. If cost, speed, experimentation, or simplicity is the actual constraint, choose the option that best satisfies it while still applying reasonable security controls.
  • The Ephemeral Compute Law: AWS Lambda is usually a poor fit for long-lived session state or large custom model weights; do not rely on Lambda memory or /tmp when the requirement calls for durable state, strict latency, or specialized execution.
  • 50/50 Purge Filter: Default to native Bedrock or serverless options when the requirement is least operational overhead or lowest cost. Do not eliminate ECS/EKS/GPU cluster patterns outright when the requirement explicitly calls for strict latency, guaranteed throughput, pre-warmed inference, or specialized runtime control.

03 End-to-End RAG Pipeline

  1. Step 1: Ingestion & Query Transformation: The client application sends the raw natural language query to the backend; optional rewriting occurs for multi-turn queries.
  2. Step 2: Vector Embedding Generation: The transformed text query is sent to an embedding model like Amazon Titan to convert the string into a high-dimensional dense vector.
  3. Step 3: Vector Database Retrieval & Hybrid Search: The query vector is sent to the vector index, such as Amazon OpenSearch Serverless or Aurora pgvector. An Approximate Nearest Neighbor (ANN via HNSW) search identifies the top-k similar chunks. k-NN Tradeoff: Increasing k increases candidate recall but degrades search performance (higher latency/compute); decreasing k speeds up search at the cost of recall.
  4. Step 4: Reranking & Context Filtering: Top candidate chunks pass through a Cross-Encoder or Reranker Model like Cohere to score true relevance.
  5. Step 5: Prompt Augmentation: The system constructs a structured prompt payload using Bedrock Prompt Management to combine context chunks, system instructions, and the user query.
  6. Step 6: Foundation Model Inference & Guardrails: The augmented prompt is passed to the Foundation Model. Amazon Bedrock Guardrails checks for prompt injections on ingress and verifies factual consistency on egress.
  7. Step 7: Response Delivery: The generated text along with chunk source citations is streamed back to the client UI in real time via WebSockets or Server-Sent Events.
Inference flowFrom prompt initiation to final answer: user prompt enters the application > request validation and auth > prompt/context assembly > retrieval and reranking > model invocation > guardrails and safety checks > token streaming or final response > observability and logging.

  • Operations: Monitor behavior over time for quality shifts and failures.

05 Vector Store Mechanics & Performance Tuning

Vector databases store dense embeddings for semantic search. Understanding how they index and scale is critical for troubleshooting retrieval latency:

  • HNSW vs. Flat (Brute Force): HNSW (Hierarchical Navigable Small World) builds multi-layer graphs for Approximate Nearest Neighbor (ANN) search with logarithmic time complexity: O(log N). Flat index performs exhaustive distance comparison across every vector in O(N) time. Always use HNSW at scale; Flat guarantees 100% recall for tiny datasets (<10k), but search latency explodes linearly as the index grows.
  • The k-NN Tradeoff (Recall vs. Latency): k specifies the number of nearest neighbors retrieved. Increasing k retrieves more candidate vectors (improving recall for downstream rerankers), but requires deeper graph traversal and larger candidate sorting, which increases query latency and degrades search performance. It never resolves slow search.
  • Segment Architecture & Refresh Interval (OpenSearch / Lucene): OpenSearch flushes vectors into immutable Lucene segments on every index refresh (default: 1s). Crucially, an HNSW graph is built per segment, and k-NN queries must search every active segment's graph before merging results. Continuous ingestion with frequent refreshes creates dozens of tiny segments, severely degrading search latency as the index grows. Fix: Raise index.refresh_interval (e.g., 30s–120s) so vectors accumulate into fewer, larger segments with unified HNSW graphs.
  • OpenSearch Serverless (AOSS) Boundaries: AOSS automatically provisions and scales OpenSearch Compute Units (OCUs) for ingestion and search. Shards and replicas are completely managed and abstracted by AWS; developers cannot configure shard counts or search replicas for Serverless collections.
  • Metadata Pre-filtering: Applying metadata filters before vector distance calculation prunes the candidate search space early, reducing search latency significantly more than adjusting k.
OpenSearch degraded search as index grows → Raise refresh interval (fewer segments/HNSW graphs); eliminate shard/replica tuning on Serverless (managed by OCUs).

06 State Management & Integration

Stateless compute / Simple independent lookups

🟢 Target: AWS Lambda, Raw Bedrock InvokeModel API, and Stateless MCP servers.
🔴 Eliminate: Provisioning persistent EC2 instances or attempting to persist session context in Lambda memory.

Stateful workflows / Multi-turn memory

🟢 Target: Amazon Bedrock Agents, Amazon DynamoDB keyed by sessionId + TTL, and AWS Step Functions Task Tokens.
🔴 Eliminate: Storing state in Lambda /tmp memory, passing entire untrimmed raw chat history from the client, and synchronous sleep loops in Lambda.

Multi-agent orchestration / shared persistent state

🟢 Target: Amazon Bedrock AgentCore Memory for managed shared memory across orchestrator and worker agents in hierarchical task execution.
🔴 Eliminate: Treating S3, DynamoDB, or ElastiCache as the default solution when the requirement is managed, shared agent state with coordination semantics.

Continuous streaming inference / IoT and event streams

🟢 Target: Amazon Kinesis Data Streams feeding Lambda or other consumers that invoke Bedrock per batch for near-real-time processing of continuous sensor or event data.
🔴 Eliminate: Scheduled polling, S3 upload triggers, or manual review patterns when the requirement is continuous streaming inference with low latency and event-driven processing.

FM provider outage / Circuit breaker

🟢 Target: AWS Step Functions Circuit Breaker pattern to fail over between foundation models.
🔴 Eliminate: Route 53 Multi-Region failover and Bedrock Cross-Region Inference.

07 Prompting, RAG & Vector Storage

Hybrid search / duplicate results

🟢 Target: Combine keyword and vector retrieval, deduplicate by document ID or normalized content, and merge relevance scores before reranking.
🔴 Eliminate: Treating keyword and vector results as separate final answer sets or disabling keyword search entirely when the requirement is hybrid retrieval.

Embedding consistency / mixed model versions

🟢 Target: Keep a single embedding model and version per vector index; all vectors in the same space must be generated by compatible encoders.
🔴 Eliminate: Mixing embeddings from different models or model versions inside one index, because they live in different vector spaces and produce unreliable similarity results.

GraphRAG / Graph relationships + vector similarity

🟢 Target: Amazon Neptune Analytics when the requirement combines related documents or entities, graph structure, and vector similarity search.
🔴 Eliminate: Treating a standalone vector store as the GraphRAG answer when the question specifically requires graph relationships or graph traversal.
S3 prompt-template governanceWhen S3 Versioning is enabled, teams can retain and restore previous versions of stored template objects.

08 Safety, Security & Networking

Cross-Region Inference / compliance boundaries

🟢 Target: Same-region inference for regulated workloads, or use explicit regional controls and networking patterns when data residency is required.
🔴 Eliminate: Treating Cross-Region Inference as compliant by default. Data can traverse regions and be subject to different regulatory requirements.

09 Testing, Evaluation & Observability

Enterprise monitoring & full observability architecture

🟢 Target: The Four-Pillar Observability Stack consisting of CloudWatch metrics, AWS X-Ray tracing, Bedrock Model Invocation Logging, and Amazon Managed Grafana.
🔴 Eliminate: Isolated CloudWatch metrics alone and weekly/batch log polling cadences.

Multi-agent systems / cross-agent observability

🟢 Target: Monitor each agent's latency, token usage, tool calls, retries, and coordination flow, then correlate traces for end-to-end task success and bottlenecks.
🔴 Eliminate: Treating a single aggregate dashboard or just the busiest agent as sufficient for diagnosing orchestration failures, handoff problems, or quality regressions across the system.

Alerting / baseline-first monitoring

🟢 Target: Establish a representative baseline for normal GenAI behavior before setting thresholds, then alert on statistically significant deviations in latency, token usage, error rate, or quality.
🔴 Eliminate: Triggering alerts on every minor fluctuation, disabling monitoring during rollout, or setting static thresholds without a baseline.

Bedrock RAG Evaluation: Citation Metrics

🟢 Target: Citation Coverage for measuring recall and completeness of source backing, and Citation Precision for measuring citation accuracy.
🔴 Eliminate: Claims that coverage applies to text while precision applies to images, execution speed pipeline claims, and custom prompt requirements.

10 Cost Optimization

Predictable queries / Reduce time to first token

🟢 Target: Pre-compute responses for common, predictable queries and serve them from an application-level response cache before invoking the Bedrock foundation model. A cache hit avoids model inference, reducing time to first token, latency, and token charges.
🔴 Eliminate: Increasing temperature, adding more few-shot examples, or assuming the InvokeModel API is inherently faster than the Converse API.
Response caching stores completed answers. Prompt Caching stores reusable prompt prefixes and still invokes the model.

Repeated system prompt + similar FAQ queries / Two-layer caching

🟢 Target: Combine Bedrock Prompt Caching for repeated system-prompt prefixes with semantic caching for similar FAQ queries. Prompt caching reduces repeated input-token charges; semantic-cache hits return stored responses without invoking the model.
🔴 Eliminate: Treating prompt caching and semantic caching as interchangeable: one reuses prompt context, while the other reuses completed answers for semantically similar requests.

Most cost-effective / Reduce token billing spend

🟢 Target: Prompt Caching for static prompt prefixes > 1,024 tokens, Batch Inference for offline processing, Model Right-Sizing, and S3 Vectors.
🔴 Eliminate: Idle dedicated instances like SageMaker multi-GPU endpoints, Flagship over-provisioning, and full raw document injection.

01 Generative AI Basics

Generative AI creates new content such as text, images, audio, code, and synthetic data from learned patterns. A foundation model is a large, general-purpose model trained on broad data and adapted to many downstream tasks.

RememberModel output is probabilistic. A fluent response is not automatically factual, current, or safe.

Common model tasks

  • Summarization: compress information while preserving key meaning.
  • Classification: assign labels, sentiment, intent, or topic.
  • Extraction: return structured fields from unstructured text.
  • Question answering: generate an answer from learned knowledge or supplied context.
  • Transformation: translate, rewrite, format, or generate code.

02 Foundation Model Workflow

StagePurpose
Pre-trainingLearn general language or multimodal patterns from large, diverse datasets.
AdaptationSpecialize behavior with prompting, fine-tuning, or preference optimization.
InferenceUse the model to produce a response for a particular request and context.
EvaluationMeasure quality, safety, latency, cost, robustness, and business fit.

Parameters are learned numerical values. More parameters can increase capability, but does not guarantee better results for every task.

03 Prompt Engineering

A strong prompt gives the model a clear task, relevant context, constraints, and an output format. Put instructions where they are easy to distinguish from untrusted input.

Task + Context + Constraints + Examples + Output format
  • Zero-shot: request a task without examples.
  • Few-shot: show representative input and output examples.
  • Chain-of-thought: for internal reasoning needs, request a concise answer or rationale appropriate to the use case rather than exposing sensitive reasoning.
  • Iterate with evaluation data; change one prompt variable at a time.

04 Amazon Bedrock

Amazon Bedrock is a fully managed service for building generative AI applications with foundation models from multiple providers through a unified API. It supports model choice, experimentation, customization, agents, guardrails, and knowledge bases.

05 RAG vs. Fine-Tuning

ApproachBest fitTradeoff
RAGCurrent, private, or frequently changing facts.Requires retrieval quality and a maintained index.
Fine-tuningConsistent style, format, behavior, or domain patterns.Needs curated data and retraining when behavior must change.
PromptingFast, low-risk behavior changes and prototypes.Less durable and can be sensitive to wording.

RAG retrieves relevant chunks, adds them to the prompt, and asks the model to answer from that context. Chunking, metadata filters, embeddings, and reranking affect retrieval quality.

Structured data ruleFor tables, CSVs, JSON, and other structured sources, use format-aware chunking that preserves schema boundaries and row/column relationships. Generic semantic chunking can keep the raw text but still destroy meaning by splitting tables across boundaries.
Preserve existing systemsWhen the requirement says to keep the existing codebase, architecture, or platform unchanged, prefer an adapter, compatibility layer, or minimal integration point over rewriting, replacing, or replatforming the current system. The goal is to add capability without breaking the consuming application.
Reduce vector search scopeWhen a RAG system has a very large document set, narrowing the search space with metadata filters or hierarchical indexes before similarity search often reduces latency much more than simply adjusting the number of retrieved chunks. Search a smaller relevant subset first; only then run vector similarity on that candidate set.

07 Responsible AI

Responsible AI means designing, deploying, and operating AI systems with fairness, explainability, privacy, security, safety, and accountability in mind. Responsibility spans the full lifecycle, not only the model.

RiskPractical control
BiasUse representative data, subgroup metrics, human review, and documented limitations.
HallucinationUse RAG, citations, constrained outputs, confidence handling, and evaluation sets.
Prompt injectionSeparate instructions from retrieved content; validate tool calls and authorize actions.
PrivacyMinimize data, redact sensitive values, control retention, and restrict access.
MisuseUse abuse monitoring, rate limits, content filters, and incident response.

08 Security Fundamentals

  • Identity: use IAM roles, least privilege, short-lived credentials, and resource policies.
  • Data protection: encrypt in transit and at rest; use AWS KMS for key management where appropriate.
  • Network controls: use VPC connectivity, private endpoints, security groups, and egress controls for sensitive workloads.
  • Observability: capture useful audit events with CloudTrail and application metrics, while avoiding secrets and unnecessary prompt retention.
  • Supply chain: validate datasets, dependencies, model artifacts, and retrieved documents.
Least privilege checkCan this identity read every document, call every tool, or change every resource? If not, scope it to the smallest required action and resource.
Bedrock Converse IAMInvoking a foundation model through the Converse API requires bedrock:InvokeModel; there is no separate bedrock:ConverseModel action.
Auditability defaultFor compliance and governance, keep enough evidence to reconstruct what happened: tool calls, request parameters, responses, timestamps, identities, and policy decisions. If the design hides or deletes interaction details, it usually fails the audit requirement.
Auditability ruleIf a question is about compliance, governance, policy enforcement, or regulator review, choose the option that preserves evidence of what the agent did. The right design keeps request data, response data, timestamps, tool calls, identities, and decisions; avoid choices that hide, delete, or erase interaction details.
Centralized governance ruleWhen the requirement is enterprise-wide policy enforcement, use one shared access layer or control plane to centralize IAM, quotas, usage tracking, and model access controls. Avoid per-team duplicates, scattered admin rights, or isolated model access paths that make governance inconsistent.
Managed service reduces ops burdenFor operational questions, favor the managed service when the requirement is to reduce patching, scaling, capacity management, and availability work. Bedrock and similar managed services shift infrastructure operations to AWS, which is why the “lower operational burden” answer is usually the correct common-sense choice.

09 Data Preparation

Quality data improves both retrieval and customization. Remove duplicates, resolve encoding problems, preserve useful structure, and document provenance.

  1. Collect data with a permitted business purpose.
  2. Clean, normalize, deduplicate, and redact.
  3. Split into representative training, validation, and test sets.
  4. Inspect labels and balance important classes.
  5. Track versions, sources, owners, and quality metrics.

10 Evaluation & Metrics

Evaluate the whole system, not just the base model. Include task quality, safety, latency, cost, and user outcomes.

Customer-service defaultFor customer-facing GenAI, “did the agent solve the user problem?” is usually a helpfulness or task-success question, not a fluency, latency, or token-count question. Generating templates, encrypting prompt text, or rewriting underperforming prompts are not the same as observing or diagnosing production behavior.

28 The Intuitive Elimination Framework

Engineering judgment gets you to the final two; AWS feature knowledge selects the winner. Common sense is a powerful filter, not a substitute for knowing documented service capabilities, limits, and configuration boundaries. (No internet or AI tools are available during the exam — trust the mental model you built.)

Core Principle The exam tests what NOT to do as much as what to do. Eliminate designs that a senior engineer would reject in production: dropping observability, removing rollback paths during a migration, skipping validation, or adding unjustified infrastructure. Then prove that the surviving option is a real AWS capability that satisfies every stated requirement.

The 4-Pass Decision Protocol

Pass 1 — Constraint Anchor: Read the LAST sentence first. Identify the binding driver: least operational overhead / lowest cost / strict latency / zero downtime.
Pass 2 — Requirement Coverage: Mark every non-negotiable, including qualifiers such as continuously, in production, without disruption, or across accounts.
Pass 3 — Red-Flag Purge: Reject anti-patterns, unsupported magic, unjustified infrastructure, and options that solve only part of the scenario. Keep plausible options provisional; do not lock out a candidate merely because wording is strong.
Pass 4 — Proof of Fit: Name the exact AWS feature, configuration, input/event source, and tradeoff that make the answer work. If you cannot explain the mechanism in one sentence, it is not proven.

Requirement Matrix

For each surviving option, silently score every mandatory requirement: ✓ directly met / ~ partly met or needs unstated work / ✗ conflicts. Select an answer only when all mandatory requirements are ✓. A technically valid design loses if it omits a qualifier or requires an unstated component.

Distractor Signatures

  • Premature teardown: Removing legacy metrics, logs, or rollback paths during migration. Preserve parallel coverage until the replacement proves stable.
  • False dichotomy: Replacing granular application telemetry with only quotas or summaries. Observability layers are usually complementary.
  • Fictional magic wand: A service “automatically” infers policy, rewrites prompts, or tunes behavior without documented configuration, rules, thresholds, or evaluation data.
  • Scope creep: Adding EKS, containers, GPUs, or bespoke orchestration without a stated control, throughput, latency, or runtime requirement that justifies it.
  • Partial solution: Solving cost but not latency, security but not auditability, or monitoring but not document-level troubleshooting.

29 Single-Select vs. Multi-Select Strategy

4-Choice Questions (Single-Select)

One option must satisfy the full requirement end-to-end. If two answers remain plausible, compare them against the Requirement Matrix and perform the Proof-of-Fit check. The winner is the one whose documented primary purpose matches the binding constraint with the fewest unstated dependencies.

5-Choice Questions (Pick Two)

The Independent-Truth Rule Test each choice independently. Select two only when each adds a required, non-duplicative control or capability and neither conflicts with the scenario. Correct answers often address different layers, but they can operate at the same layer when they provide defense in depth or different evidence/control functions.
Complementary Pattern Example

Caching layersPrompt prefix cache + Semantic response cache

Named-Feature Rule

When a question asks which Bedrock, AgentCore, SageMaker, Guardrails, or CloudWatch feature provides a behavior, expect a named managed capability. Do not substitute a reasonable DIY architecture unless the managed feature cannot meet the requirement. Learn lifecycle distinctions: online vs. on-demand evaluation; knowledge-base ingestion logs vs. model invocation logs vs. CloudTrail; Prompt Management vs. prompt caching vs. response caching.

30 Absolute-Language Verification

Words such as always, never, immediately, solely, and automatically are prompts to verify a service boundary — not instant disqualifiers.

  • Eliminate the option when the claim conflicts with the requirements or documented behavior.
  • Keep it when a stated security, compliance, reliability, or availability requirement justifies the strong language and AWS supports the capability.
  • Without configuration is suspect unless the service explicitly performs that behavior by default.
  • Automatically detects / infers / decides requires a documented classifier, evaluator, threshold, rule, or managed feature.
Final rule: Common sense eliminates bad architecture; AWS service knowledge chooses the supported one. Preserve baselines during migrations, use canary or parallel telemetry when appropriate, and verify capability + configuration + workload fit before committing.
